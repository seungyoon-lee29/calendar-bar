- 메뉴막대 표시 연결: Orca 표시를 끄면 CalendarBar 개별 허용이 켜져 있어도 blocked host가 되는 현상을 재현했다. 2026-09-28 ControlCenter `trackedApplications`의 Orca 항목에 정상·QA·Runtime QA CalendarBar 세 식별자가 함께 저장된 것을 확인하고, 17:42 해당 세 연결만 제거했다. 원본 Data의 권한 0600 백업과 쓰기 직전 동일성 검사, 단일 키 쓰기 exit 0, 구조 차이가 세 연결 삭제뿐임과 다른 키·허용 상태 보존, 별도 재조회에서 수정 유지까지 확인했다. 실제 Orca 표시 끄기에서 아이콘·팝오버 유지와 앱 재실행 후 연결 재생성 여부는 아직 미검증이므로 해결 완료로 처리하지 않는다. 전역 초기화·ControlCenter 재시작·로그인/알림 설정 변경은 수행하지 않았다.
- 재로그인: 실제 로그인 항목 등록과 enabled 상태를 확인했다. 실제 로그아웃 후 자동 실행까지 확인하려면 사용자 세션 종료가 필요하므로 수행하지 않았다.


- 최초 알림 권한 요청 실패의 원인이 남아 있다. `Sources/CalendarNotifications/Module.swift:88`의 권한 요청은 새 합성 QA 번들의 직접·LaunchServices·Finder 실행에서 오류 안내로 끝났다. 시스템 설정에서 독립 QA 항목이 꺼져 있었고, 해당 Runtime QA 항목만 켠 후 같은 앱에서 실제 예약 2개가 확인되어 예약 경로는 진행했다. 최초 요청이 허용 대화상자를 열지 못한 환경 원인은 미확정이다. 유효 서명 identity 0개라는 사실만으로 원인을 단정할 수 없다.
- `Sources/CalendarBar/main.swift:29`의 실제 알림 클릭 진입은 자동 라우터 테스트와 별개다. 두 합성 트리거 전에 앱을 종료했으나 컴퓨터 사용 도구가 알림 센터에서 날씨 위젯 창만 선택해 QA 배너·클릭을 직접 확인하지 못했다. 전역 공유/미러링 중 알림 정책은 꺼져 있었으나 다른 앱 개인정보에도 영향을 주므로 변경하지 않았다. 동일 ID의 원본 실행 파일 진단 복사본은 허용=2, 대기=0, 전달=0을 반환했지만 재빌드 코드 해시 차이도 있어 도착 증거로 사용하지 않는다. 2026-09-28 사용자가 “알람보여”라고 응답해 실제 시험 알림 표시는 수동 확인했다. 콜드·웜 실행의 실제 알림 클릭과 목적 날짜·행 강조는 아직 확인되지 않았다. 사용자 클릭 결과 확인 또는 같은 설치본으로 해당 경로를 다시 검증해야 하며, 확인 전 기능 전체를 완료로 표시하지 않는다.
- 실제 계정의 분리된 반복 발생분 취소와 원거리 이동을 구별하는 조합은 합성 테스트까지만 확인했다. `Sources/CalendarAccess/EventKitBackend.swift:64`의 직접 확인이 범위 밖일 때 삭제로 단정하지 않고 확인 필요로 남기지만, 계정 제공자별 반환을 보장하려면 사용자가 관리하는 원본의 읽기 전용 대조가 필요하다. 현재 검증은 원본 쓰기가 금지되어 이 조합을 임의 생성하지 않았다.

- 시험 알림을 누르면 알림만 사라지고 앱 화면이 열리지 않는다는 사용자 보고가 확인됐다. 2026-09-28 16:55 합성 예약 전에 QA 프로세스를 종료했고, 클릭 뒤 새 QA 프로세스가 생긴 것은 확인했다. 따라서 앱 실행 자체와 화면 표시·목적지 전달을 나누어 진단한다. `Sources/CalendarUI/CalendarAppCoordinator.swift:63`의 표시 요청과 `Sources/CalendarBar/main.swift:34`의 재열기 경로를 회귀 검증 중이며 아직 원인을 확정하거나 해결했다고 보고하지 않는다. 기존 실제 클릭 미확인 항목은 이 결함 수정·재검증으로 해소해야 한다.

# 남은 확인 사항

- 메뉴막대 표시 연결: 이 맥의 ControlCenter가 최초 개발 실행의 CalendarBar를 Orca 아래에 묶었다. Orca 표시를 끄면 CalendarBar 개별 허용이 켜져 있어도 blocked host가 된다. 현재 두 표시를 켜 두었다. 다른 시스템 표시 설정을 초기화하거나 보호된 설정 파일을 수정하지 않았다.
- 재로그인: 실제 로그인 항목 등록과 enabled 상태를 확인했다. 실제 로그아웃 후 자동 실행까지 확인하려면 사용자 세션 종료가 필요하므로 수행하지 않았다.


- 실제 OS 알림 도착·클릭 확인이 남아 있다. `Sources/CalendarNotifications/Module.swift:88`의 권한 요청은 새 합성 QA 번들의 직접·LaunchServices·Finder 실행에서 오류 안내로 끝났다. 시스템 설정에서 독립 QA 항목이 꺼져 있었고, 해당 Runtime QA 항목만 켠 후 같은 앱에서 실제 예약 2개가 확인되어 예약 경로는 진행했다. 최초 요청이 허용 대화상자를 열지 못한 환경 원인은 미확정이다. 유효 서명 identity 0개라는 사실만으로 원인을 단정할 수 없다.
- `Sources/CalendarBar/main.swift:29`의 실제 알림 클릭 진입은 자동 라우터 테스트와 별개다. 두 합성 트리거 전에 앱을 종료했으나 컴퓨터 사용 도구가 알림 센터에서 날씨 위젯 창만 선택해 QA 배너·클릭을 직접 확인하지 못했다. 전역 공유/미러링 중 알림 정책은 꺼져 있었으나 다른 앱 개인정보에도 영향을 주므로 변경하지 않았다. 동일 ID의 원본 실행 파일 진단 복사본은 허용=2, 대기=0, 전달=0을 반환했지만 재빌드 코드 해시 차이도 있어 도착 증거로 사용하지 않는다. 사용자 알림센터 확인 또는 같은 설치본으로 다시 예약·종료·클릭 확인이 필요하며 이 확인 전 기능 전체를 완료로 표시하지 않는다.
- 실제 계정의 분리된 반복 발생분 취소와 원거리 이동을 구별하는 조합은 합성 테스트까지만 확인했다. `Sources/CalendarAccess/EventKitBackend.swift:59`의 직접 확인이 범위 밖일 때 삭제로 단정하지 않고 확인 필요로 남기지만, 계정 제공자별 반환을 보장하려면 사용자가 관리하는 원본의 읽기 전용 대조가 필요하다. 현재 검증은 원본 쓰기가 금지되어 이 조합을 임의 생성하지 않았다.
